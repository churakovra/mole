# MOLE 1.0.0 — руководство по разработке с Codex

> **Версия руководства:** 1.0 · 2026-11-08  
> **Назначение:** пошаговая инструкция, как использовать два согласованных документа, вести разработку, проверять качество и довести MOLE до релиза `1.0.0`.  
> **Подход:** один небольшой PR за раз → тесты → независимое ревью → исправления → merge → следующий PR.

## 1. Три документа и их роли

Поместите эти **три файла рядом**, предпочтительно в корень создаваемого GitHub-репозитория `mole/`:

| Файл | Роль | Когда использовать |
|---|---|---|
| [`MOLE-1.0.0-IMPLEMENTATION-PLAN.md`](MOLE-1.0.0-IMPLEMENTATION-PLAN.md) | **Нормативное архитектурное ТЗ:** границы релиза, ADR, модули, протокол, SKM, безопасность, тесты, критерии 1.0.0 | Перед проектированием; для разрешения разногласий и приёмки |
| [`MOLE-1.0.0-PR-BACKLOG.md`](MOLE-1.0.0-PR-BACKLOG.md) | **План выполнения:** PR-01…PR-14, зависимости, конкретные задачи и Definition of Done | Перед каждой итерацией и для отслеживания прогресса |
| `MOLE-1.0.0-DEVELOPMENT-GUIDE.md` (этот файл) | **Операционный процесс:** как работать с Codex, Git, тестами, ревью и передачей контекста | В ежедневной разработке |

**Приоритет при противоречиях:** безопасность и архитектурные ADR из Implementation Plan → явные acceptance criteria соответствующего PR из Backlog → этот Guide. Если обнаружено реальное противоречие, зафиксировать его в ADR/decision log и согласовать изменение, а не молча выбирать удобную интерпретацию.

**Уже известное расхождение:** стартовый prompt в §18 Implementation Plan предлагает начать с PR-01 и PR-02, а Backlog рекомендует **PR-01 only**. Для управляемой разработки применяем **PR-01 only**, затем отдельный PR-02 после ревью и приёмки PR-01.

### Что из старого скилла использовать

Архив `workflow-diagram-explorer(1).zip` — **референс продуктового поведения**, особенно вложенные диаграммы, навигация, редактирование, zoom/pan и объяснения. Он **не** должен становиться генератором по принципу «модель копирует и переписывает demo HTML». Новый renderer строится по данным SKM.

## 2. Фундаментальные договорённости, которые нельзя потерять

1. **Пользовательский Agent Skill:** `mole` (`name: mole`, вызов `$mole` в Codex); **внутренний движок:** `molekit`.
2. **Self-contained payload:** всё нужное для выполнения лежит в `skills/mole/`; копирование только этой директории не ломает скилл.
3. **Установка:** не требуется отдельный Python package, PyPI, MCP, Node, Docker, API-key или сетевой bootstrap. Базовый runtime — **Python 3.11+ / stdlib**.
4. **Script-first, LLM-guided, evidence-driven:** Engine индексирует, извлекает, связывает, проверяет, экспортирует; LLM отвечает за смысл и сложные неоднозначности, отправляя *semantic patches*.
5. **Никаких скрытых обращений к LLM из Engine.** Агент вызывает локальный CLI (`start / next / inspect / submit / status / finish`); Engine владеет state machine и рабочим состоянием `.mole/`.
6. **SKM — единый источник истины** для Markdown, offline single-file HTML, `.drawio` и дополнительного Mermaid.
7. **Markdown обязателен**, не просто пояснение к диаграмме; материалы должны быть понятны без HTML.
8. **Evidence discipline:** статический возможный вызов не равен доказанному runtime-вызову; все существенные утверждения подтверждены или явно помечены `inferred` / `unknown` / `contradicted`.
9. **Нет выполнения кода анализируемого проекта** или установки его зависимостей по умолчанию; нет скрытых сетевых обращений и автопубликации.
10. **Ручные правки не перетираются:** при обновлении возможны merge и явные конфликты.
11. **Python-first для 1.0.0.** Не пытаться сделать все языки одинаково точными; неподдерживаемые сценарии обозначать как reduced coverage.
12. **Релизные claims только после тестов.** `NOT_RUN` нельзя выдавать за `PASS`; Confluence integration без тестового tenant/app не считать проверенной.

Изменения этих пунктов — отдельное осознанное архитектурное решение, не случайный рефакторинг в очередном PR.

## 3. Подготовка Git-репозитория (один раз)

### 3.1. Создайте проект

Рекомендуемое имя репозитория: `mole` (это рабочий выбор; доступность и возможные конфликты названия нужно проверить при публикации).

Минимальная стартовая структура:

```text
mole/
├── MOLE-1.0.0-IMPLEMENTATION-PLAN.md
├── MOLE-1.0.0-PR-BACKLOG.md
├── MOLE-1.0.0-DEVELOPMENT-GUIDE.md
└── ...  # код появится в PR-01
```

Если используете уже существующий репозиторий, поместите эти три файла в одну директорию и убедитесь, что относительные ссылки между ними работают. **Никакой код MOLE ещё не реализован этими документами.**

### 3.2. Базовые настройки процесса

- Основная ветка: `main`.
- Рабочая ветка: `feature/pr-01-skill-bootstrap`, далее аналогично для каждого PR.
- Один PR = **один конкретный пункт** из Backlog.
- Не смешивать изменения разных PR без необходимости; если обнаружена зависимость, описать её и согласовать перестановку.
- Для каждого PR: тесты + отчёт исполнителя + независимое ревью + исправления + повторная проверка.
- Не просить агента автоматически пушить, мержить, публиковать релиз или устанавливать инструменты. Делать эти действия явно по своему решению.

Пример создания ветки (после инициализации репозитория и наличия `main`):

```bash
git switch main
git pull --ff-only   # только если настроен remote; иначе пропустите
git switch -c feature/pr-01-skill-bootstrap
```

**Важно:** `git pull` — пользовательская операция работы с собственным репозиторием, а не разрешение MoleKit скачивать зависимости или код исследуемого проекта во время анализа.

## 4. Как запускать разработку в Codex

### 4.1. Первая сессия

1. Откройте репозиторий `mole` в Codex.
2. Убедитесь, что три `.md`-файла доступны в рабочей директории. При необходимости приложите их в разговор.
3. Создайте ветку под PR-01.
4. Отправьте **Prompt A** ниже.
5. После завершения проверьте diff, реальные тесты и результат; не переходите автоматически к PR-02.

#### Prompt A — старт проекта, PR-01

```text
Ты реализуешь open-source Agent Skill MOLE 1.0.0.

Прочитай три файла полностью:
- MOLE-1.0.0-IMPLEMENTATION-PLAN.md — нормативная архитектура и требования;
- MOLE-1.0.0-PR-BACKLOG.md — границы PR, DoD и зависимости;
- MOLE-1.0.0-DEVELOPMENT-GUIDE.md — наш процесс разработки.

Начни ТОЛЬКО с PR-01 из Backlog. Сначала кратко сформулируй scope,
проверяемые требования и последовательность реализации; затем реализуй
работающий код, тесты и документацию в рамках PR-01.

Обязательно:
- public skill называется mole, внутренний движок molekit;
- весь runtime payload самодостаточен внутри skills/mole/;
- Python 3.11+, stdlib-only core; никаких pip/uv/npm/MCP;
- не выполнять код исследуемых репозиториев и не делать network calls;
- никаких placeholder implementations под видом готовых функций;
- тестировать КОПИЮ только skills/mole/ вне корня репозитория;
- если что-то нельзя проверить, явно напиши NOT_RUN и почему.

В конце представь:
1) изменения и архитектурные решения;
2) git diff summary;
3) команды тестов и их реальные результаты;
4) выполненные/невыполненные пункты DoD PR-01;
5) риски, ограничения и вопросы для ревью.

Не реализуй PR-02 и не делай commit/push/merge без отдельного запроса.
```

### 4.2. Каждый следующий PR

После принятия предыдущего PR создайте новую ветку от актуального `main` и используйте Prompt B. Не отправляйте агенту только «сделай следующий этап»: **явно называйте PR и проверяйте DoD**.

#### Prompt B — реализация конкретного PR

```text
Мы продолжаем MOLE 1.0.0. Изучи актуальный код и три документа:
MOLE-1.0.0-IMPLEMENTATION-PLAN.md,
MOLE-1.0.0-PR-BACKLOG.md,
MOLE-1.0.0-DEVELOPMENT-GUIDE.md.

Текущая задача: PR-XX — <название PR из Backlog>.
Предшествующие PR: <перечень уже принятых PR>.

Сначала оцени реальные зависимости от уже реализованных компонентов,
кратко сформулируй план и acceptance criteria этого PR.
Делай только изменения, необходимые этому PR; соблюдай существующие
архитектурные контракты и тестируй все новые пути, включая ошибки.

Не переходи к PR-(XX+1). Не создавай пустые заглушки.
Не устанавливай зависимости и не выполняй target repo code без согласования.
Не пиши «тесты пройдены», если не запускал их.

В конце дай отчёт по шаблону из Backlog и чеклист DoD данного PR,
перечисли реальные команды тестирования и их результаты, риски,
несовместимости и то, что требует моего решения.
Не делай commit/push/merge без отдельного запроса.
```

Подставьте реальные номер, название и список принятых PR. Не заменяйте номер PR на «следующий» — так проще предотвратить scope creep и ошибочное продолжение.

## 5. Правильный цикл одного PR

```text
main (проверенная база)
    │
    ├── feature/pr-XX-...
    │     1. Прочитать ТЗ и DoD
    │     2. Спроектировать только этот срез
    │     3. Реализовать реальные функции + тесты
    │     4. Запустить нужные проверки
    │     5. Независимое ревью
    │     6. Исправить замечания и повторить проверки
    │
    └── merge в main → зафиксировать статус → следующий PR
```

| Шаг | Ответственный | Результат |
|---|---|---|
| Выбрать PR и сверить зависимости | Вы + Codex | Чёткий scope, acceptance criteria |
| Реализовать | Codex | Код и тесты без несогласованных побочных изменений |
| Проверить локально | Codex | Логи тестов, список `PASS/FAIL/NOT_RUN` |
| Проверить дифф | Вы / отдельный reviewer-агент | Замечания по correctness, архитектуре, безопасности, поддерживаемости |
| Исправить | Codex | Минимальный patch + повторный прогон тестов |
| Принять и объединить | Вы | Merge/commit, обновлённые статусы и базовая ветка |

**Не переходить к следующему PR**, если у текущего остались P0/P1-проблемы, не выполнен обязательный DoD или сомнительно соответствие ADR. Для P2/P3 допускается явно зарегистрированный технический долг, если он не нарушает релизные критерии.

## 6. Как проводить независимое ревью

Лучше использовать отдельную Codex-сессию/агента с задачей **review-only**, чтобы он не оправдывал собственную реализацию. Дайте ему diff, код, планы и результаты тестов. Без доступа к реальному коду и логам полноценное ревью невозможно.

#### Prompt C — review-only

```text
Проведи строгое независимое code review текущего PR-XX проекта MOLE.
Требования и контекст: MOLE-1.0.0-IMPLEMENTATION-PLAN.md,
MOLE-1.0.0-PR-BACKLOG.md, MOLE-1.0.0-DEVELOPMENT-GUIDE.md.

Изучи git diff относительно целевой ветки и затронутый код/тесты.
Ничего не меняй. Проверь:
- полноту DoD конкретного PR;
- корректность алгоритмов и отсутствие скрытых заглушек;
- соответствие ADR, расположение ответственности по слоям;
- обработку ошибок, инварианты SKM, стейт-машины, протокола;
- безопасность (target-code execution, network, secrets, injection,
  path traversal, unsafe HTML/XML/MD);
- backwards compatibility, отмену/повторы/resume и negative tests;
- простоту расширения, связанность, дублирование и мёртвый код;
- достаточность реальных тестов и фактические NOT_RUN.

Верни замечания в порядке P0/P1/P2/P3. Для каждого укажи
file:line, воспроизводимый сценарий или обоснование, последствия
и минимально разумное исправление. Если дефектов не найдено,
перечисли оставшиеся риски и что реально проверено.
Не приписывай проекту отсутствующие функции.
```

Приоритеты:

- **P0** — уязвимость, потеря данных, небезопасная операция, фундаментальная ошибочность / сломанный основной сценарий.
- **P1** — нарушенный обязательный контракт/DoD, существенная ошибка, ложное доказательство, недостоверный экспорт.
- **P2** — заметный дефект UX, тестируемости или поддерживаемости без немедленного риска.
- **P3** — необязательное улучшение или стилистика, не блокирующая этап.

#### Prompt D — исправление замечаний

```text
Исправь замечания независимого ревью к PR-XX.
Сначала проверь каждое замечание по реальному коду: не исправляй
неподтверждённые предположения без объяснения.

Выполни только необходимые правки в scope текущего PR.
Добавь regression tests для подтверждённых дефектов, запусти их,
повтори относящиеся к PR проверки и обнови итоговый отчёт.

Выведи таблицу: замечание → подтверждено/отклонено → правка
→ тест → результат. Не переходи к следующему PR, не делай push/merge.
```

Ревью может обнаружить дефект в старом коде, вне scope текущего PR. Если он блокирует текущую работу — исправить в согласованном объёме; если нет — отдельный issue/PR, не бесконтрольное расширение изменений.

## 7. Как тестировать и принимать работу

### Минимальный набор проверок для каждого PR

1. `git diff --check` и осмотр изменённых файлов.
2. Тесты изменённого модуля с реальными результатами.
3. Негативные сценарии: invalid JSON, missing source, permission denied, corrupted state и т. п. — в зависимости от PR.
4. Проверка соответствия архитектурным ADR и DoD из Backlog.
5. Сводка `PASS/FAIL/NOT_RUN` с обоснованием для каждого невыполненного обязательного теста.
6. Проверка «скрытых» действий: зависимости не устанавливаются, код target repo не исполняется, сеть не используется без явного разрешения.

### На каких PR ключевые проверки особенно важны

| PR | Главный тестовый фокус |
|---|---|
| 01 | Только `skills/mole/` скопирован в temp dir; `doctor` и `--help` работают без сети/зависимостей |
| 02 | State machine, атомарные записи, resume, idempotency, invalid transitions |
| 03 | Schema v1, refs/provenance, raw candidates vs runtime evidence |
| 04–05 | AST, adapters, false positive/negative edges, таймауты, исключения, unsupported syntax |
| 06 | Сжатый `next/inspect`, валидный `submit`, stale patches и bounded agent loop |
| 07 | Markdown самостоятельно объясняет процесс; ссылки и ручные заметки сохраняются |
| 08–10 | Один data-driven offline HTML; responsive UX, доступность, правки и regenerate |
| 11 | `.drawio` round-trip, multipage/links, ограничения в Confluence; NOT_RUN без tenant |
| 12 | Changed-revision, инвалидация кэша, сохранение заметок и конфликты |
| 13 | Security, portability, agent eval, браузерный регресс, benchmarking токенов |
| 14 | Чистая установка и end-to-end; все обязательные quality gates и релизные артефакты |

### Команды (только когда соответствующая реализация уже существует)

```bash
# Пример базового запуска после PR-01
python3 skills/mole/scripts/mole.py doctor --json
python3 skills/mole/scripts/mole.py --help

# Пример системного тестирования с Python stdlib
python3 -m unittest discover -s tests -p 'test_*.py'

# Проверка git diff
git diff --check
```

**Не копируйте команды как доказательство выполнения**: они только шаблоны. Если тестовый runner или команда ещё не реализованы, используйте реализованный эквивалент и честно фиксируйте `NOT_RUN`.

### Перед финальным `1.0.0`

Обязательно сверить **§13 и §15 Implementation Plan** целиком, включая golden fixtures, сквозные E2E, реальные доказательства, OS matrix, browser UX, XSS/секреты, offline HTML, `.drawio`, возврат к старой модели после прерывания и сохранение ручных правок.

**Confluence:** работоспособный локальный `.drawio` и руководство импорта обязательны; если нет доступного тестового Confluence Cloud с draw.io app, интеграционный smoke = `NOT_RUN`. Не утверждать, что он прошёл.

## 8. Как сохранять контекст между Codex-сессиями

Создайте **`DEVELOPMENT-STATUS.md`** в репозитории и обновляйте его **после принятого PR**. Этот файл содержит только операционный статус, не дублирует тысячи строк ТЗ.

Рекомендуемый шаблон:

```markdown
# MOLE 1.0.0 — Development Status

- Baseline: main @ <commit-sha>
- Current PR: PR-01 — Packaging / self-contained skill
- Current branch: feature/pr-01-skill-bootstrap
- PR state: IN_PROGRESS  <!-- TODO | IN_PROGRESS | IN_REVIEW | CHANGES_REQUESTED | ACCEPTED | MERGED -->
- Accepted PRs: none
- Blocking issues: none
- Non-blocking follow-ups: none
- Tests last run: <commands + result + date>
- Architecture decisions: see MOLE-1.0.0-IMPLEMENTATION-PLAN.md §1
- Next action: complete PR-01 DoD and request independent review
```

Новые Codex-сессии начните с просьбы прочитать этот файл, оба плана и актуальный diff. **Не рассчитывайте на память модели о предыдущих сессиях.** Проверять состояние в Git и файловой системе, а не только по рассказу агента.

#### Prompt E — продолжить после перерыва

```text
Продолжаем MOLE 1.0.0 после перерыва.
Прочитай DEVELOPMENT-STATUS.md и три документа планирования.
Сверь содержимое статуса с реальным Git (ветка, коммиты, diff)
и текущим кодом. Кратко скажи, что действительно завершено,
что заблокировано и какая следующая разрешённая задача.

Продолжай только текущий PR с его DoD; не переходи к следующему,
пока текущий PR не принят. Ничего не публикуй и не устанавливай.
```

### Как вести changelog / ADR

- **Architecture decision:** если поменяли исходное решение D-01…D-22, оформите маленькую ADR-запись: контекст, варианты, решение, последствия, миграция и обновление нормативного плана.
- **Changelog:** фиксируйте пользовательски заметные изменения, особенно схемы данных, CLI и поведения HTML Explorer.
- **Backlog:** отмечайте выполненные задачи только после принятия PR; неполные или отложенные обязательные требования не скрывайте.

## 9. Карта из 14 PR: порядок и checkpoints

| Фаза | PR | Результат для проверки |

## 10. Как не потерять качество при активном использовании AI

**Антипаттерны, которые запрещаем:**

- Просить «реализуй всю версию 1.0.0 за один заход», не фиксируя границы PR.
- Говорить «tests pass» без фактического запуска и логов.
- Принимать «валидный JSON» как доказательство правильности бизнес-утверждения.
- Подменять универсальный diagram renderer условными координатами и ручными SVG-фрагментами для конкретной demo-схемы.
- Устанавливать тяжёлые зависимости ради ускорения PR-01 или скрыто скачивать parser при `scan`.
- Переносить фрагменты исходников и секреты в HTML/документацию без review.
- Реализовывать MCP, PyPI, SaaS или Forge раньше закрытия основных сценариев 1.0.0.
- Позволять агенту переписывать документацию пользователя при повторном запуске.
- Мержить без проверки сквозного сценария, если PR меняет CLI/SKM/export контракт.

### Важное про эффективность токенов

На этапе **разработки** Codex может использовать столько анализа, сколько действительно требует задача. Экономия токенов, о которой мы договаривались, прежде всего относится к **работе готового MOLE**: встроенный Engine механически извлекает facts, а модель получает лишь компактные задачи с evidence. При разработке же приоритет — корректность, а не минимальное число вызовов модели.

### Когда можно изменить план

План — нормативный, но не догма. Если эксперимент показывает, что определённый parser, подход к layout или контракт неработоспособен, сначала оформите evidence (тест/benchmark/PoC), затем обновите ADR и backlog и только после этого меняйте архитектуру. Не принимайте масштабное решение по одному красивому demo.

## 11. Политика принятия PR и релиза

PR считается **ACCEPTED**, если:

- Реализован утверждённый scope, выполнены обязательные пункты DoD.
- Результат не содержит незакрытых P0/P1 и скрытых заглушек.
- Тесты и проверки реально выполнены; `NOT_RUN` объяснены и не скрывают обязательный блокер.
- Дифф читаем, нет неожиданного изменения соседних подсистем.
- Внесены нужные записи в статус и документацию, а пользователь подтвердил готовность к merge.

После **PR-14** релиз возможен только при соответствии §15 Implementation Plan. Публикация GitHub release/tag, настройка установщика и любые внешние действия — отдельные осознанные операции, не автоматическое следствие готовности кода.

## 12. Самый короткий сценарий для ежедневной работы

1. Сверьте `DEVELOPMENT-STATUS.md` и текущую ветку.
2. Откройте в Codex три документа и отправьте Prompt B для **одного** PR.
3. Проверьте фактические тесты и diff.
4. Запустите отдельное review-only ревью (Prompt C).
5. Исправьте замечания (Prompt D), повторите тесты.
6. Примите PR, обновите статус, объедините в `main`.
7. Создайте новую ветку и только тогда начинайте следующий PR.

**Начинать с PR-01. Останавливаться на границе каждого PR.** Это основной способ превратить большой план в последовательную, контролируемую и поддерживаемую реализацию MOLE 1.0.0.
